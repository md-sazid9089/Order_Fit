## 1. Scope of the engine

The engine answers one question for one proposed order: given existing obligations, expected receipts, the cash balance and the owner's constraints, which parameterized strategies keep cash at or above the minimum reserve on every calendar day, what do they cost, how much headroom do they keep, how do they behave under user-specified stress, and what would change the answer. It does not forecast the business, price risk, or predict customer behavior. Scenarios are user-specified shifts, never probabilities.

Out of scope for the engine in the MVP (detected and escalated, never guessed): taxes and VAT, foreign exchange, business-day and holiday calendars, several orders at once, variable-rate loans, barter or crypto payments, penalties and discounts not entered as explicit events. **Deferred levers** (the reference code keeps them, no MVP fixture uses them, and each has a known issue recorded in the review log): staged delivery (it only delays receipts and becomes an artefact when combined with an advance), deferring the start (no dependency model, no supplier-cost shift), and the receivable-advance financing shape (its repayment moves with the receipt, which makes feasibility non-monotone in delay; same-day netting of the advance is unresolved).

## 2. Units and conventions (mandatory financial semantics)

| Rule | Definition |
|---|---|
| Money | `int` minor units inside the engine (BDT: 2 decimals, `exponent = 2`). Never floats. `Decimal` or decimal strings only at the API edge. A `Money` value is `{amount_minor, currency}`; one currency per deal; a different currency on any amount is `E-UNSUPPORTED-MULTICCY` because no FX rate is ever assumed. |
| Rounding | One rule: `apply_bps(amount, bps) = (amount * bps + 5000) // 10000` (round half up, non-negative inputs only). Used for fees, interest, discounts, surcharges, deposits, overruns. Splits into equal parts give the remainder to the last part, so parts sum exactly. |
| Dates | Calendar dates (ISO 8601, no time of day). The `as_of` date is the first day of the horizon and is stored with every evaluation; every dated input before it is rejected (`E-DATE-IN-PAST`). |
| Payment terms | A term names an anchor event (`order`, `delivery`, `invoice`, `goods_receipt`), a length in calendar days and a convention. Only the convention `calendar` is supported; any other convention is `E-UNSUPPORTED-CONVENTION`. An unknown anchor is `E-MISSING-ANCHOR` (ask, or proceed on a flagged reading if every reading gives the same recommendation). |
| Same-day order | Within one date all outflows are applied before all inflows. The day's **trough** is the balance after outflows and before inflows. |
| Certainty | Each cash event is `confirmed`, `expected` or `assumed`. Scenarios shift or reduce only non-confirmed customer receipts, the deposit and non-confirmed existing collections. The interface always shows the class beside every date and amount; an expected payment is never displayed as confirmed. |
| Provenance | Every material field carries `uploaded`, `extracted`, `user_confirmed`, `assumed` or `derived` (section 10.2). |
| Horizon | Auto horizon = latest possible event under any scenario or strategy (latest dated event + terms + largest delay + largest extension) plus 30 days, and at least the longest financing term plus lead. A payment beyond a user-stated window extends the window; it never silently disappears (case M-12). |
| Reserve | The minimum cash reserve `R` is an absolute amount. It is a hard constraint on every calendar day, **applied relative to the baseline** (section 3): the order must not push the balance below `min(R, baseline balance)`. "At the reserve passes; one minor unit below breaches" (strict `<`, case B-02). |
| Input hash | `sha256` of the canonical JSON (keys sorted, minimal separators, integers only) of the engine input only: no labels, no intent, no document text, no named strategies. Both the reference and the production engine use this definition, so a stored result is comparable byte for byte. |

## 3. Calculation definitions

Let `D = {as_of, ..., H_end}`, `R` the reserve, `B0` the opening balance at the start of `as_of`.

**Events.** `e = (id, date, amount_minor > 0, direction in {in, out}, kind, certainty, scope in {baseline, order, financing}, provenance)`.

**Daily series.** For day `t`: `outs(t)`, `ins(t)` are the sums on that date. `trough(t) = close(t-1) - outs(t)`, `close(t) = trough(t) + ins(t)`, `close(as_of - 1) = B0`. The series is produced for every calendar day. Because balances change only on event dates, checking every day is mathematically equivalent to checking event dates plus the start date `[I]`; the daily series is kept for display and alerts.

**Lowest balance** = `min_t trough(t)`; **lowest date** = earliest `t` attaining it. **Headroom** = lowest balance - `R` (negative means a breach). **First shortfall date** = earliest `t` with `trough(t) < R` (absolute). **Absolute gap** = `max_t (R - trough(t))+`.

**Counterfactual.** The baseline series `base_S(t)` uses baseline events only, under the same scenario `S`. The required level on day `t` is `L_S(t) = min(R, trough_base_S(t))`. A strategy **violates** on day `t` if `trough_strategy_S(t) < L_S(t)`. It is **feasible in scenario S** if it never violates. This isolates the order's effect: where the baseline already sits below the reserve (pre-existing breach, case B-01), the order must not make it worse, and the pre-existing breach is reported separately as `E-PRE-EXISTING-BREACH`. **Maximum funding gap** = `max_t (L_S(t) - trough(t))+`: the extra cash needed on the worst day.

**Order economics** (incremental only; cases B-03, "no double counting"):

```
concession_bps          = deposit_discount_bps + deposit_discount_bps_per_10pct * deposit_pct / 10   [only if a deposit is asked]
revenue_net             = revenue - apply_bps(revenue, concession_bps)
incremental_costs       = sum(cost lines with incremental = true) + extension surcharges
order_profit_before_financing = revenue_net - incremental_costs
financing_cost          = fees + interest   (repayment of principal is not a cost)
net_order_profit        = order_profit_before_financing - financing_cost
```

The concession a customer asks for a deposit grows with the deposit (a flat part plus a part per 10 points), so a larger ask costs more profit and ties between deposit sizes are broken by economics, not by the grid. A cost line with `incremental = false` (for example inventory already owned) is excluded from both profit and cash and is listed in the output. A cost line that re-states an invoice already in the baseline (`invoice_ref` match) is rejected as `E-DUPLICATE-OBLIGATION`; one with the same amount within 3 days and no reference raises `W-POSSIBLE-DUPLICATE`; so each obligation is counted once. Cash inflows are never profit: the fixture `OF-03` has 2,000,000.00 of customer cash and a net order profit of -300,000.00, and is declined.

**Customer receipts.** Receipt date = date of the anchor event + term days (one final receipt in the MVP). With a deposit of `p` percent: deposit = `apply_bps(revenue_net, p * 100)` received `deposit_lead_days` after the order date (default 7, assumed); the remainder is the final receipt.

**Scenarios.** `base` applies nothing. `downside` and `severe` are user-specified records with these fields (all assumed and editable; the defaults of the fixtures are in brackets): `order_receipt_delay_days` (customer pays late; 15 and 45), `ar_delay_days` (the owner's other customers pay late; 5 and 15), `cost_overrun_bps` (incremental costs rise; 0 and 300), `order_receipt_haircut_bps` (partial payment; 0), and `deposit_follows_customer_delay` (default true: **a customer who pays late also pays the deposit late**). Confirmed events never move. After the review the deposit is no longer exempt from stress: with the old exemption the recommended plan looked robust to 45 days only because the lever that made it robust was not stressed.

**Financing events** use only user-supplied offer terms and are separate dated events (proceeds, fee, interest, repayment). MVP shape `term_loan`: draw date `max(as_of + lead_days, available_from)`, repayment `draw + term_days` (fixed), cost `apply_bps(P, fee_bps) + fee_flat + apply_bps(P, interest_bps)` (flat per term), events `loan_draw` in, `loan_fee` out (at draw or repayment, `fee_at`), `loan_interest` out, `loan_repayment` out. An offer whose `valid_until` is before the draw date is ineligible. Amounts `P` lie on the offer grid `min, min + step, ..., max`. Financing cost is checked against the owner's cap across all scenarios. The deferred shape `receivable_advance` (repaid on the customer-payment date, fee growing with days outstanding) stays in the reference code only.

## 4. Strategy space

A strategy is a small parameter record, enumerated exhaustively (no solver, no random search):

| Parameter | Values (per case) | Dependency created |
|---|---|---|
| `deposit_pct` | a grid, 5-point steps up to 50 in the anchor case | customer |
| `ext_days` (+ `ext_surcharge_bps`) | 0 or 30 days on cost lines marked `deferrable` | supplier |
| `offer_id` + `loan_minor` | none, or one offer with an amount | lender |
| `decline` | order refused (the baseline) | none |

Loan sizing is enumeration, not a formula: for each combination of the other levers and each offer, scan amounts upward on the offer grid and keep the **smallest amount that is feasible in the base scenario and also in the named scenario**, for each of `base`, `downside` and `severe` (up to three sized variants when they differ). A candidate must always hold in the base scenario, because the base case is the hard constraint. Feasibility is not monotone in the loan amount (a bigger loan means a bigger repayment on a fixed date), so no direction is assumed (case L-06).

**Dominance pruning.** A strategy is dropped from the ranked list if a strict sub-plan (same values on the shared levers, fewer levers) is at least as profitable, at least as resilient and has at least as much cash on its lowest day in every scenario: the extra lever only adds a dependency. Pruned strategies are counted in the output (`dominated_pruned`).

## 5. Constraints and objectives

**Hard constraints** (a strategy that fails any is never recommended; soft preferences never override them):

1. Reserve rule on every calendar day in the base scenario (section 3, counterfactual form).
2. `financing_cost <= owner.max_financing_cost` in every scenario, when the owner set a cap.
3. `net_order_profit > owner.min_order_profit` (default 0): an order that loses money after its own costs is not recommended (case O-02 strategic mode needs an explicit owner override, logged).

**Resilience level and the owner's target.** Level 0 fails the base scenario; 1 passes base; 2 passes base and downside; 3 passes base, downside and severe. The owner sets a **target** scenario (`base`, `downside` or `severe`; default `downside`). The target is **soft**, not a hard constraint: a strategy `meets_target_resilience` if its level reaches the target's level; plans that do not are ranked below plans that do, and if the best plan does not meet the target the engine escalates `E-FRAGILE-BEST`. (An earlier draft called this "required"; the name was misleading and was changed.) Every plan also reports its **headroom** (section 3) in each scenario, because a level of 2 with 71,200.00 of headroom is not the same as a level of 2 with 400,000.00.

**Ranking.** Among hard-feasible strategies the order is lexicographic, with these keys in this order:

```
1. meets_target_resilience  (yes before no)
2..k. the owner's priority list, in the owner's order, each one of
        profit              higher net_order_profit first
        independence_any    fewer external parties (customer, supplier, lender) first
        independence_customer  no customer dependence first
        simplicity          fewer levers first
        low_financing_cost  lower financing cost first
        robustness          higher resilience level first
final deterministic tie-breaks: smaller loan, smaller deposit, smaller extension, id
```

Why lexicographic and not a weighted score: the weights would be invented numbers with no ground truth; lexicographic ordering has no weights, makes the explanation exact ("A ranks above B because the first criterion on which they differ is profit"), and keeps hard constraints structurally ahead of preferences. Default priorities `[profit, independence_any, simplicity]` `[A]`. A lexicographic rule has no bound on the profit given up for resilience, so every recommendation reports `profit_given_up_for_resilience` (the best hard-feasible profit minus the recommended plan's profit) and names the highest-profit plan. A learned or language-model ranker is an optional plug-in that may only reorder strategies the engine already verified ([ADR 0006](adrs/0006-orchestration-and-learned-layer.md)).

## 6. Uncertainty, missing information and escalation

**Delay scan** (linear, one-parameter): feasibility is evaluated for customer-receipt delay `d = 0, 1, ..., scan_days` (default 90), delaying the customer and, by default, the deposit, with everything else as in the base scenario. `tolerance_days` = the last delay before the first failure; `-1` = fails even if paid on time (shown as "fails even on time", case X-02); `survives_full_scan` = no failure up to `scan_days` (shown as "safe within the scanned range", case X-01). **Why linear.** For the MVP levers the response is monotone: delaying an inflow can only lower the balance on every date, so feasibility, once lost, is never regained; `selftest.py` confirms this on all 52 enumerated strategies of `OF-02` and `OF-04`. A binary search would therefore have been valid for the MVP, and the linear scan is kept because it is exact by construction, costs at most 91 sweeps per strategy, and stays correct if a lever is added whose outflow moves with the receipt: for the deferred receivable-advance shape the self-test finds strategies whose feasibility is non-monotone in delay. (An earlier draft and the repository's ADR 0002 asserted non-monotonicity from an example in the team's catalogue that does not exist in the chart; the earlier fixture instance depended on the deferred shape, so the claim is now stated for that shape only.)

**Best plan by delay.** `best_plan_by_receipt_delay` scans `d = 0..scan_days` over the dominance-pruned, base-feasible shortlist and reports each delay at which the best plan *among those that hold at that delay* changes, ranked by the owner's priorities, and the first delay at which no shortlisted plan holds. It answers "if only my customer is late by `d` days, which plan do I want", which is **a different question from the recommendation**: the recommendation uses the full downside scenario (the owner's other customers late, the deposit late) and the owner's target, and need not equal the best plan at any single delay.

**Sensitivity to the assumed parameters.** Because the recommendation is only as good as the assumed scenario parameters, `assumption_sensitivity` re-runs the whole analysis with one assumed parameter at a time set to stated values (concession per 10 points, downside customer delay, other customers' delay, severe cost overrun, deposit lead) and lists the values at which the recommendation changes. It is a first-class output next to the recommendation.

**Missing information (value of information).** If a required field is missing or ambiguous, the engine does not compute with a guess. For each uncertain input the caller supplies alternatives; the engine runs the full analysis for each. If the recommended strategy or decision class differs between alternatives, the workflow asks the owner (`E-ASK-INPUT` or `E-MISSING-ANCHOR` with the alternatives shown); if it does not differ, the analysis proceeds on the most conservative reading (the latest customer-payment date), shows `A-ASSUMED-INPUT` and names the other readings. Required inputs with no default: opening balance, reserve, payment-term anchor and days, every cost date and amount, customer payment amount. Inputs with a documented default shown in the output as `assumed`: `deposit_lead_days` (7), the scenario parameters of section 3, the concession per 10 points of deposit (the owner must enter it; the fixtures use 50 bps), the close-call margin (200 bps).

**Escalation, blocking and warning codes** (all deterministic; blocking means no recommendation is shown, escalating means the result is shown but the owner must acknowledge):

| Code | Kind | Trigger |
|---|---|---|
| `E-MISSING-ANCHOR`, `E-MISSING-ANCHOR-DATE` | needs input | payment anchor unknown or has no date (and the readings differ) |
| `E-ASK-INPUT` | needs input | an unresolved input flips the recommendation (value of information) |
| `E-DATA-CONFLICT`, `E-DUPLICATE-OBLIGATION`, `E-INVALID-QUANTITY`, `E-DATE-IN-PAST` | blocking | PO total versus quote total or line items disagree; an order cost re-states a baseline invoice; non-positive quantity; date before `as_of` |
| `E-UNSUPPORTED-MULTICCY`, `E-UNSUPPORTED-TAX`, `E-UNSUPPORTED-CONVENTION`, `E-UNSUPPORTED-FINANCING`, `E-INVALID-AMOUNT` | unsupported | outside the supported semantics |
| `E-NO-FEASIBLE` | escalate | no strategy satisfies the hard constraints; the output includes the maximum funding gap of accepting as-is, the smallest customer deposit that would work alone (if any), and the first violation date even with a 100% deposit |
| `E-UNPROFITABLE-AFTER-COSTS` | escalate | cash-feasible strategies exist but none clears the owner's minimum order profit |
| `E-FRAGILE-BEST` | escalate | the best strategy does not reach the target resilience; the output includes the deposit percentage at which a deposit-only plan would be robust, if any |
| `E-PRE-EXISTING-BREACH` | escalate | the baseline already breaches the reserve |
| `E-CLOSE-CALL` | escalate | the top plan beats a plan with a different dependency set on profit by no more than `close_call_bps` (default 200, `[A]`), both meet the target resilience, and that plan is better on another priority key or on resilience: a real trade-off the owner should decide |
| `W-BASELINE-COVERAGE` | warning | baseline events end before the order's last possible receipt: obligations after the data ends are not modelled |
| `W-POSSIBLE-DUPLICATE` | warning | an order cost has the same amount as a baseline outflow within 3 days and no invoice reference |
| `A-ASSUMED-INPUT` | flag | an ambiguous input was resolved by value of information on the most conservative reading |
| `F-INJECTION` | flag | instruction-like text found in a document (a signal for the owner, never the defence; section 11) |

**Alerts** (Topic E "cash-flow management with alerts"): `A1 reserve breach` (first shortfall date, balance, gap), `A2 payment before receipt` (the first violating day and the next inflow date after which the balance is back at the reserve, with the days exposed) and `A6 pre-existing breach` are computed by the reference engine for the accept-as-is plan and the recommended plan; `A5 stale approval` is raised by the workflow when an input changes after approval; `A3 overdue receivable` and `A4 offer expiry` need the sandbox clock and are IF-TIME. In `OF-02`, accepting as offered raises A1 on 2026-12-07 (balance -50,000.00, 650,000.00 below the reserve) and A2 with 52 days exposed until the customer pays on 2027-01-28.

## 7. Engine interface (function signatures)

Pure functions; no I/O, no clock, no randomness, no LLM. The only caller in the application is the workflow's `evaluate` step ([03](03-system-architecture.md)).

```python
Money = TypedDict("Money", {"amount_minor": int, "currency": str})

def apply_bps(amount_minor: int, bps: int) -> int: ...
def split_exact(total_minor: int, parts: int) -> list[int]: ...

def validate_case(case: CaseInput) -> tuple[list[Flag], list[BlockingError]]:   # raises NeedsInput / Unsupported
def horizon_end(case: CaseInput) -> date: ...
def build_events(case: CaseInput, strategy: Strategy, scenario: Scenario) -> list[CashEvent]: ...
def sweep(opening: int, events: list[CashEvent], start: date, end: date) -> dict[date, tuple[int, int]]:   # (trough, close) for every day
def scenario_metrics(case, strategy, scenario, ...) -> ScenarioMetrics:      # lowest, headroom, shortfall dates, funding gap, feasibility, financing cost
def enumerate_strategies(case: CaseInput) -> list[Strategy]:                 # includes loan sizing for three scenarios and decline
def evaluate(case: CaseInput, strategy: Strategy) -> StrategyResult:         # 3 scenarios, profit, cost, resilience level
def rank(results, owner) -> RankedResult
def delay_scan(case, strategy, scan_days) -> DelayScan
def ranking_by_delay(case, shortlist, scan_days) -> list[RankChange]
def alerts_for(case, result) -> list[Alert]
def assumption_sensitivity(case, base_recommendation) -> Sensitivity
def voi(case) -> list[VoiResult]
def analyse(case: CaseInput) -> Evaluation                                    # the single entry point; deterministic
def slot_values(evaluation) -> dict[str, str]; def render_slots(text, slots) -> tuple[str, list[str]]   # section 11
```

`analyse` is reproducible: `Evaluation.input_hash` is the input hash of section 2 and is stored with `calc_version`, so any stored result can be re-run and compared after a code change. The production engine starts as the reference engine (vendored, typed at the edges), so parity with `fixtures/expected/` is exact and compared on the canonical JSON.

A second implementation of the series calculation (`bruteforce_series`: one event at a time, tracking the running minimum) is cross-checked against `sweep` on every strategy of every fixture and must stay in the test suite. It re-sums the same events that `build_events` produced, so it checks the sweep, not the event semantics (concessions, loan dates, certainty). The event semantics are checked by the two historical reproductions (section 8) and, before submission, by a teammate who did not write the engine hand-computing two cases from the inputs.

## 9. Worked example (anchor case `OF-02`)

Shapla Packaging Ltd (synthetic, Dhaka, BDT). As-of 2026-11-02, opening balance 2,150,000.00, minimum reserve 600,000.00. Existing obligations: rent 120,000.00 on the 10th, loan installment 150,000.00 on the 25th, payroll 450,000.00 near month end, one supplier invoice (INV-1007) of 380,000.00 on 2026-11-15. Expected collections from other customers: 700,000.00 on the 20th of each month. Order PO-8841: revenue 3,600,000.00, customer pays 45 days after delivery (delivery 2026-12-14, so payment on 2027-01-28, `expected`). Incremental costs: supplier deposit 900,000.00 (2026-11-04), supplier balance 900,000.00 (2026-12-07, deferrable), plates and labour 300,000.00 (2026-12-10), freight 100,000.00 (2026-12-14). Order profit before financing = 3,600,000.00 - 2,200,000.00 = **1,400,000.00**. A customer asked for a deposit will want a concession of 50 bps of revenue per 10 points of deposit (40% costs 72,000.00; `assumed`). One user-supplied financing offer `BANK_WC` (term loan, 5 days to draw, 90 days, 1% fee at draw, 3% flat interest, 500,000.00 to 2,500,000.00 in steps of 100,000.00); it is a fixture, not a market quote. Stress (all `assumed`, editable): downside = customer 15 days late, other customers 5 days late, deposit delayed with the customer; severe = customer 45 days late, other customers 15 days late, costs 3% higher. Target resilience: the downside.

**Counterfactual.** Baseline lowest balance 1,570,000.00 (2027-03-10): no pre-existing breach. Accepting as offered: lowest balance **-590,000.00 on 2027-01-10**, first day below the reserve **2026-12-07** (the day the 900,000.00 supplier balance is paid), maximum funding gap **1,190,000.00**, 53 days in which the order itself breaches. The order is profitable and unaffordable as offered. Alerts A1 and A2 fire (section 6).

**Strategies** (45 enumerated, 7 dominated and pruned, 14 failing the reserve, 23 hard-feasible; the top six by the ranking rule):

|---:|---|---|---:|---:|---:|---:|---:|---:|
| 1 | `dep40` | customer | 1,328,000.00 | 0.00 | 221,200.00 | 71,200.00 | -1,236,000.00 | 2 |
| 2 | `dep40+ext30` | customer, supplier | 1,328,000.00 | 0.00 | 221,200.00 | 71,200.00 | -477,000.00 | 2 |
| 3 | `dep45` | customer | 1,319,000.00 | 0.00 | 393,550.00 | 150,000.00 | -1,236,000.00 | 2 |
| 4 | `dep45+ext30` | customer, supplier | 1,319,000.00 | 0.00 | 393,550.00 | 150,000.00 | -477,000.00 | 2 |
| 5 | `dep35+fin:BANK_WC@500,000.00` | customer, lender | 1,317,000.00 | 20,000.00 | 542,950.00 | 7,950.00 | -741,000.00 | 2 |
| 6 | `dep35+ext30+fin:BANK_WC@500,000.00` | customer, supplier, lender | 1,317,000.00 | 20,000.00 | 542,950.00 | 7,950.00 | -658,050.00 | 2 |

Single levers fail: a 30% deposit alone leaves a lowest balance of 473,800.00 in the base case; a 30-day supplier extension alone leaves -590,000.00.

**The trade-off.** The highest-profit hard-feasible plan is a 1,300,000.00 bank loan (profit **1,348,000.00**, financing cost 52,000.00, no customer ask), but it is the most fragile: its repayment of 1,300,000.00 plus 39,000.00 interest falls on 2027-02-05 and it survives a late customer payment only up to 7 days; at 8 days (the customer pays on the repayment day, outflow first) it breaches, and in the downside scenario (the customer pays 2027-02-12) its lowest balance is -662,000.00 on 2027-02-10. The recommended plan is the 40% deposit (1,411,200.00 received on 2026-11-09 after the 72,000.00 concession): profit 1,328,000.00, **20,000.00 less** than the loan (1.5%), no financing, and it holds the downside scenario with **71,200.00 of headroom** (lowest balance 671,200.00 on 2027-01-25). Its prices are a dependency on the customer's consent and thin headroom.

**Nothing survives the severe case, and the agent says so.** Of the 30 hard-feasible plans none reaches resilience level 3: the best in the severe scenario, a 50% deposit with a 30-day supplier extension and a 500,000.00 loan, is still 141,000.00 below the reserve on its worst day, and the recommended `dep40` is 1,236,000.00 below (the deposit then arrives on 2026-12-24, after the supplier balance falls due). If the severe scenario were only "the customer pays 45 days late" six plans would reach level 3 (a check run for this document): the conclusion depends on the other customers and the costs also being stressed. The owner chooses the target; the recommendation does not claim 45-day robustness.

**What would change the answer.** `best_plan_by_receipt_delay`: with only the customer late, the loan is the best plan from 0 to 7 days late, `dep35` from 8, `dep35+ext30` from 28, `dep35+ext30+fin:BANK_WC@500,000.00` from 31, `dep40+ext30+fin:BANK_WC@500,000.00` from 41, and from 58 days late no shortlisted plan holds. The sensitivity table (one assumed parameter at a time): the recommendation stays `dep40` for any concession from 0 to 150 bps per 10 points, any deposit lead from 3 to 14 days and any severe cost overrun from 0 to 500 bps; it changes with the **downside customer delay** (5 days: the loan `fin:BANK_WC@1,400,000.00`; 10 and 20 days: `dep40`; 30 days: `dep40+ext30`) and with the **other customers' delay** (0 days: `dep35`; 10 or 15 days: `dep35` plus a 600,000.00 loan). The recommendation is therefore only as good as the owner's view of how late the customer and the other customers can be, and the output says so. With the owner's target set to `base` the ranking flips to the loan plan and the engine flags `E-CLOSE-CALL` (the deposit plan is within 1.5% of its profit and is more resilient; `OF-07A`); with the target at the downside and customer independence first, it stays on `dep40` (`OF-07B`). If the customer will pay at most 30%, the best remaining plan is the loan again (profit 1,348,000.00) but it fails the downside and the engine escalates `E-FRAGILE-BEST`, adding that a deposit-only plan would become robust at **38%** (`DEMO-REPLY`).

**Same profit, different decision.** `OF-15` (order B, revenue 2,800,000.00, customer pays in 30 days, supplier balance of 800,000.00 due after the customer pays) has the same order profit before financing, **1,400,000.00**, but accepting as offered leaves a lowest balance of 1,010,000.00: decision `accept_as_is`. The difference is payment timing and supplier terms, not profit.

**Escalation and the missing-information loop.** In `DEMO-ASK` the purchase order says "Net 45" without a start event. Read from the invoice date (2026-11-06, a pro-forma invoice) the best plan is `ext30+fin:BANK_WC@500,000.00`; read from delivery it is `dep40`. The recommendation differs, so the engine returns `needs_input` and the agent asks the owner which reading the contract uses instead of choosing.

**A five-line rule versus the engine.** On the 14 analysable core fixtures the greedy ladder (accept if feasible, else the smallest feasible deposit alone, then an extension alone, then the smallest loan alone) picks the same plan as the engine in 9. It picks `dep35` in the anchor, a plan that fails the owner's downside target (headroom -102,050.00), where the engine picks `dep40`; it also accepts two orders whose net profit is below the owner's minimum (`OF-03`, `OF-06`) because it never checks profit. See [`fixtures/baselines.md`](fixtures/baselines.md) and [05](05-security-and-evaluation.md) section 6.4.

## 10. Data contracts

### 10.1 Storage choice and retention

Relational storage (PostgreSQL). Reason: approvals, idempotency keys, the hash-chained operation log and tenant isolation need transactions and foreign keys; evaluation results are stored as `jsonb` next to typed columns for lookup. A document store would make these guarantees application-side. Tenant isolation is enforced by application-level scoping and a non-owner application role (mandatory) and, as hardening, Row-Level Security with `FORCE ROW LEVEL SECURITY` ([ADR 0004](adrs/0004-persistence-and-isolation.md)). Retention: demo data is synthetic and kept until the demo environment is reset; for any real use the owner deletes a deal (`DELETE /v1/deals/{id}`), which removes documents, fields, events and evaluations, and leaves a tombstone entry in the operation log (the log holds hashes, ids and masked values, not document content, and has no foreign key to the deal). Jurisdiction-dependent retention and data-protection obligations are open questions (section 9 of [01](01-requirements-scenario-edge-cases.md)).

### 10.2 Entities (the smallest consistent set: 15)

Types: `id` = UUID; `ts` = UTC timestamp; `money` = `amount_minor bigint` + `currency char(3)`; enums are lowercase strings. Every table has `business_id`, except `business` itself. `prov` = provenance in `{uploaded, extracted, user_confirmed, assumed, derived}`.

| Entity | Key fields | Notes |
|---|---|---|
| `business` | id, name, currency, default_reserve (money), synthetic bool, created_at | tenant root; one currency; `synthetic = true` is required for `live` model mode |

### 10.4 Error contract

Errors are `{ "error": { "code": "...", "message": "...", "retryable": false, "field": null, "escalation_code": null }, "request_id": "..." }`. User-facing errors (shown with an action) differ from internal failures (shown as "something went wrong", with the `request_id` only; stack traces and internals never leave the server).

| HTTP | `code` | Meaning | User-facing? |
|---|---|---|---|
| 400 | `VALIDATION_FAILED` | schema or range error (field named) | yes |
| 401 / 403 | `UNAUTHENTICATED`, `FORBIDDEN`, `TIER_DENIED`, `APPROVAL_REQUIRED`, `STEP_UP_REQUIRED` | no session; role too low; tool above the state's tier; T3 without approval; approval without the step-up | yes |
| 404 | `NOT_FOUND` | also returned for another tenant's id | yes |
| 409 | `STALE_INPUT_VERSION`, `STALE_EVALUATION`, `APPROVAL_INVALID`, `DUPLICATE_DOCUMENT`, `NEEDS_INPUT`, `EXECUTION_IN_PROGRESS` | edit conflict; result no longer current; approval voided or hash mismatch; same sha256 uploaded; a question must be answered (`escalation_code` set); an edit during execution | yes |
| 422 | `UNSUPPORTED_INPUT`, `DATA_CONFLICT` | outside supported semantics or contradictory documents (`escalation_code` set) | yes |
| 429 | `RATE_LIMITED` | per-tenant limit | yes |
| 503 | `LLM_UNAVAILABLE` | degrade to manual entry; the engine still runs | yes |
| 500 | `INTERNAL` | unexpected failure | no (request id only) |

### 10.5 Reproducibility of a recommendation

A recommendation is reproducible from five stored items: the `input_version` rows (fields, events, offers, constraints), `calc_version`, the scenario assumptions, the strategy enumeration rules, and `input_hash`. Re-running `analyse` on the stored inputs with the same `calc_version` must give an identical result (compared by canonical JSON). A change to engine code that can alter any result must bump `calc_version`; tests re-run stored evaluations of the fixtures.

### 10.6 Baseline cash events: the input the owner has to supply

For a made-to-order SME the 25 to 30 rows of payroll, rent, installments and expected collections are the real work, not the arithmetic. The MVP accepts a CSV, or the same fields typed in a table, with a downloadable template and these rules:

| Column | Rule |
|---|---|
| `date` | ISO date, not before `as_of` |
| `direction` | `in` or `out` |
| `amount` | positive decimal with at most 2 decimals, in the deal's currency (no currency column: one currency per deal) |
| `kind` | one of the enumerated kinds of section 10.2 |
| `certainty` | `confirmed`, `expected` or `assumed` (existing collections default to `expected`) |
| `counterparty`, `invoice_ref`, `note` | optional; `invoice_ref` powers the duplicate check |

Opening balance and the reserve are entered in the form, not the CSV. Validation errors name the row and column. Coverage is checked: if the last baseline event is earlier than the order's last possible receipt the evaluation carries `W-BASELINE-COVERAGE` ("obligations after the data ends are not modelled"), so a missing second month of payroll is visible rather than silent. Sample row: `2026-11-30,out,450000.00,payroll,confirmed,staff,,monthly payroll`. The sample file is generated from `fixtures/cases/OF-02.json` at build time.

## 11. Explanation slots and extraction grounding

**Explanation (slot-based).** The model returns text with **named slots only** (`{{plan:dep40}}`, `{{profit:dep40}}`, `{{asis_lowest}}`); code resolves each slot to a labelled phrase built from the evaluation ("net order profit of plan dep40: 1,328,000.00"), so a value cannot be attached to the wrong plan. Text is rejected, and the deterministic template shown instead, if it contains any digit in any script (Unicode category Nd), any number word in English, Bengali or Hindi (a short list in the reference), any URL or address marker, or any slot not in the evaluation. This replaces an earlier verifier that tested each number for membership in one set of allowed numbers and was shown, by the reviewer, to pass swapped figures, sign flips, other-script number words and URLs. Verified in `selftest.py`: a slot text resolves with no problem; digits, non-ASCII digits, English, Bengali and Hindi number words, URLs and unknown slots are each rejected. Roman numerals and other scripts are not covered (a known limit), which is why the owner still reads the text before it is sent.

**Extraction grounding.** The model returns typed fields with a page and a quote. Deterministic code then normalises whitespace and Unicode in both the document text and the quote (PDF text extraction breaks table cells and wraps lines; a literal comparison would mark correct fields `conflicting`), checks that the quote occurs in the document text, and that the number or date parsed from the quote equals the value (South Asian formats such as `5,00,000`, `5L` and `0.5 crore` are normalised, case D-10; an ambiguous date such as `03/04/2026` becomes `ambiguous` and is asked, case D-11). A field that fails the check is `conflicting`. Arithmetic cross-checks (line items sum to the total, PO total equals quote total) are recomputed in code. The owner confirms every extracted number before the engine runs, with the source highlighted. Grounding cannot tell a hidden clause from a visible one: a hidden but literal quote is a real quote. Where two quotes in the same document give different values for the same field, both are shown and the field is `conflicting`. This is a control, not a guarantee (known risk in [05](05-security-and-evaluation.md)).

**Injection scan.** `injection_scan` is a small regex flagger used to warn the owner. It is not a defence: the defence is structural (document text can only populate typed, owner-confirmed fields; the language model has no tools; money fields come from the engine). `selftest.py` shows the scan catches the two catalogue strings (D-05, D-12) and stays quiet on a normal sentence; a paraphrase would evade it, which is why it carries no security weight.
